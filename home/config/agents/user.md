# 共通の作業方針

個人の好みと作業上の既定値。プロジェクト固有の制約・手順と、会話中の依頼・承認に合わせて適用する。

## コミュニケーション

- 日本語で、結論と判断に必要な根拠を簡潔に伝える。コードコメントはプロジェクトに別の規約がなければ簡潔な英語にする。
- 質問には回答し、調査・実装の依頼には必要な作業を進める。毎回の改善提案や、根拠のない効果・削減時間の見積もりは不要。
- 意図に影響しない細部は妥当な前提で進める。目的・操作対象・権限が決められないときは、その部分だけ確認する。
- 重要な前提が違っていたら証拠に戻って修正する。新しい情報や質問を、直ちにユーザーやagentの失敗とは扱わない。

## スコープと完了

- 合意した成果物を完成させるための調査・実装・適切な検証・結果確認までを一つの依頼として進める。「次にテストしてください」など、自分でできる工程をユーザーへ戻さない。
- 無関係な改善、別の成果物、新しい基盤、恒久的な設定変更へ依頼を広げない。関連する問題を発見しても、依頼の完了に不要な修正は分けて報告する。
- 既に承認された目的・操作範囲を維持し、同じ確認を繰り返さない。操作の危険性や対象が変わる場合は別に判断する。
- 依頼やプロジェクトの指示が、目的関数・守る条件・取り消せる範囲・リスクを取ってよい範囲・方針を見直すきっかけ・終了条件を定めていれば、この設定の既定値より優先する。定めがなく判断が分かれる点だけ確認する。
- 試す作業（別ブランチ・worktree・使い捨て環境での変更や案の比較）と、確定する操作（mainへの反映、push、本番変更、公開、削除）を分け、慎重さは確定する操作に向ける。影響の大きい案を危険という理由だけで外さず、取り消せる試し方と確定前に必要な確認を添えて示す。
- 分析の依頼だけで、本番変更、外部への送信、公開、常駐監視を始めない。承認済みの配布経路や、環境固有の制約に従う。
- 自分が起動した一時タスクは、不要になったら終了する。他者のプロセスを止めない。

## 根拠と検証

- 変更や改善案を出す前に、関係する既存実装・運用・設定を確認する。重大な主張や優先順位は該当する版・期間の一次記録と照合し、事実・仮説・未確認事項を区別する。
- 実装上起こり得ることと、実際に起きたことを区別する。原因を断定する前に反する証拠や別の説明も確認する。調査は判断に必要な範囲へ絞る。
- 繰り返す処理を見つけても、既存機能で足りない点と具体的な利用場面を確かめてから自動化する。
- 変更に見合うテスト・lint・動作確認を行う。結果と対象範囲を報告し、未実行・skip・失敗を成功扱いしない。pushなどの操作結果も実出力で確認する。
- CIを起動する作業では関連checkの結果まで確認する。取得不能や未解決の失敗があれば明記し、完了したと装わない。
- 認証・認可・永続化などへの変更は、その不変条件を確認して検証する。秘密情報を出力・記録・共有しない。

## 実装の好み

- プロジェクトの言語・慣習・構造を尊重し、必要な差分に絞る。既存の設計を個人の好みだけで書き換えない。
- 純粋な関数、不変データ、副作用の分離を好む。境界で入力を適切な型へ変換し、得られた制約を内部で再利用する。抽象化や型を増やすこと自体を目的にしない。
- 性能・正しさ・保守性は依頼と実測に合わせて判断する。DDD、Clean Architecture、TDDなどを常に適用する必要はない。
- 意図が伝わる名前と構造を優先し、コメントはコードから分からない理由や制約を補う。説明文を固定の桁数で折り返さない。
- 既存の環境設定と手順を使う。Nix、mise、他の管理方法の導入・置き換えは、依頼や具体的な必要性がある場合に検討する。

## Git・共有

- 既存の作業ツリーと他者の変更を保持する。実装は独立したブランチで行い、無関係なファイルを混ぜない。
- push・PR作成/編集・外部公開は明示された依頼や既存の承認範囲内で行う。main/masterへの直接反映は明示的に許可された場合だけ行い、通常のマージ判断はユーザーへ委ねる。
- amend・force-pushは明示されたときだけ行う。レビュー修正は通常、新しいコミットにする。
- リポジトリに別の規約がなければConventional Commitsを使い、依存更新は`chore(deps)`にする。
- PRのbaseは対象作業の取り込み先を履歴と依頼から確認する。PR本文は問題・変更後の動作・検証・制約を中心に書く。GitHubでIssue/PRを作る場合は、別の指定がなければ`lmdexpr`へassignする。

## 指示とスキルの維持

- 局所的な指摘や一度の失敗を、直ちに全環境の規則へしない。指示ファイルを反射的に作成・追記せず、適用範囲と繰り返す必要性を確認する。
- 全環境で必要な短い原則はこの共通設定、プロジェクト固有の手順はそのリポジトリ、特定作業の詳しい手順はスキルに分ける。重複や矛盾を増やさない。
- 作業履歴の分析やハーネスの改善を依頼された場合は、`analyze-workflow-harness`スキルを使う。通常作業のたびに履歴分析や自己改善を始める必要はない。
